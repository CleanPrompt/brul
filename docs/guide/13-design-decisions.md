# 13. Design decisions

Every design is a set of choices. This chapter explains the important ones: what was chosen, what the alternative
was, and why. You should be able to defend these choices, or argue for a different one.

The complete list is the decisions table in `docs/implementation-plan.md`.

## Architecture

| Decision | Alternative | Why this choice |
|---|---|---|
| Feature-first folders | Layer-first (`controllers/`, `services/`, ...) | Everything about one feature is together; features can be added and removed as a unit |
| Manual wiring in `Application.kt` | A DI framework (Koin, Spring) | 30 readable lines, nothing to configure, nothing magic to explain |
| Repository interface + Exposed implementation | Services call Exposed directly | Services can be tested with fakes; database code stays in one layer |
| Separate DTOs and domain models | Send the models as JSON | A password hash can never leak; the JSON contract can change without touching the model |
| Mappers as extension functions | Mapper classes, or conversion inside services | Short, idiomatic (`user.toResponse()`), and easy to find |
| JetBrains Amper | Gradle | Much less build configuration for a single-module project |

## Security

| Decision | Alternative | Why this choice |
|---|---|---|
| JWT access tokens | Server-side sessions | Stateless and the usual choice for a mobile client |
| Token version (`ver` claim) for logout | A blocklist of revoked tokens; refresh tokens | One column, no extra table. Trade-off: logout ends all sessions of that user |
| Permissions read from the database per request | Roles inside the token | A revoked role works immediately, also for tokens already issued |
| Permissions as a Kotlin enum | Free strings in the database | A typo is a compile error; every permission has code that checks it |
| Roles not creatable via the API | Full role management | A runtime role has no meaning without code that checks its permissions |
| `BOOTSTRAP_ADMIN_EMAIL` for the first admin | A seeded admin with a default password | No password in code or configuration; works on an empty database |
| Same error for unknown email and wrong password | Specific errors | Callers cannot discover which emails are registered |
| BCrypt, cost 12 | Fast hashes (SHA-256) | Deliberately slow, salted: brute force becomes impractical |
| Rate limit on login, registration and password change | No limit | Slows down password guessing |

## API design

| Decision | Alternative | Why this choice |
|---|---|---|
| `/api/v1` prefix | No version | A breaking change can later go to `/api/v2` while v1 keeps working |
| UUIDs as ids | Auto-increment numbers | Cannot be guessed or counted; generated by the server |
| One error shape `{ code, message }` | Different shapes per endpoint | One piece of client code reads every error |
| Exceptions mapped centrally in `StatusPages` | Error responses built in routes | Routes stay short; one place to change |
| Users deactivated, never deleted | Hard delete | History and references stay valid; an admin can reactivate |
| Feedback deleted for real | Soft delete | No history worth keeping; also shows the contrast with users |
| Separate endpoint for the feedback status | A status field in the normal `PATCH` | Each route has exactly one access check |
| Wrong current password → 400 | 401 | The token is valid; a client treats 401 as "session expired" |

## Lists

| Decision | Alternative | Why this choice |
|---|---|---|
| Query parameters on each list endpoint | One global `/search` endpoint | Each feature knows its own filters and access rules |
| Offset paging (`limit`, `offset`) | Cursor paging | Easiest to understand and to explain; fine for this amount of data |
| `PageResponse { items, total, limit, offset }` | A bare JSON array | The client can show "page 2 of 5" and knows when to stop |
| `LIKE '%text%'`, escaped | Full-text search (Lucene, H2 fulltext) | Good enough here; full-text search is a new technology to learn and explain |
| Fixed sort fields per feature | Any column name | A client cannot sort on sensitive columns |
| Invalid parameter → 400 | Silently use a default | Mistakes are noticed |

## Things deliberately left out

| Left out | Why | When you would add it |
|---|---|---|
| Database migrations (Flyway) | An extra tool to learn; `SchemaUtils.create` is enough during development | As soon as there is a production database whose data must survive schema changes |
| Refresh tokens | More endpoints and storage | When users should stay logged in for weeks without re-entering a password |
| Email verification, password reset by email | Needs an email service | For a public app |
| Swagger UI | An extra dependency | `openapi.yaml` already documents the contract |
| PostgreSQL | H2 needs no installation | For production; only `repository/` code and configuration would change |

## How to make a new decision

When you add something to the project, ask:

1. **Can I explain every line?** If not, it is too complex.
2. **Does it follow the existing pattern?** Copy `feedback` before inventing something new.
3. **Does it need a new library?** Then discuss it first. Every dependency is something everyone must understand.
4. **Write it down.** Add a row to the decisions table in `docs/implementation-plan.md`: topic, decision, reason.
